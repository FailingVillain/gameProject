# N13 지도 크기별 부하 시험 (2026-10-19)

측정만 했고 게임 코드 · 밸런스는 바꾸지 않았다. 추가한 것은 읽기 전용 측정 도구 `--mapload` (`src/Tests/MapSizeLoad.cs`, Program.cs 한 줄) 뿐.
`KoreanDivision --mapload size=N k=K scene=E|A|C ticks=300` — 프로세스당 한 칸만 잰다. Release (`-p:OutputType=Exe`), 워밍업 60틱 + 측정 300틱, 시드 기본, 2인, 안개 켬, AI 컨트롤러 없음.

- 구성: 보병 82% · 정찰 2% · 기병(총기병) 8% · 기관총 3% · 야전포 3% · 곡사포 2%. 전차 · 대전차소총 없음.
- 장면: **E** 빈 지도 (시작 병력 140기만) · **A** k 기가 흩어져 서 있음 (전투 거의 없음) · **C** 양측 k/2 덩어리가 서로 공격 이동 (대규모 교전).
- 표의 `기수` 는 측정 끝 시점 생존 수 (A 에서는 포병/기병이 서로 쏴서 일부 감소).

## 1. 결론 (먼저)

1. **면적에 비례해 커지는 비용의 정체 = 공간 해시 재구성 `World.RebuildHash` (World.cs 326행)**. 유닛 수와 무관하게 틱마다 두 번 (UpdateUnit 앞 `hash1`, 뒤 `hash2`) 지도 전체 칸을 훑는다:
   `Array.Clear(cellStart / cellMask / coarseMask)` + 접두합 루프 `for c<cells` + `Array.Copy(cellStart → cellCursor)`. 전부 O(칸 수) = O(지도 면적).
   빈 1200² · 140기: 틱 1.93 ms 중 hash1 0.98 + hash2 0.99 = **1.97 ms (≈ 100%)**. 1500² 3000기: 틱 5.9 ms 중 해시 4.2 ms (71%).
   칸당 약 0.7 ns × 2회 (1200² = 144만 칸 → 회당 1.0 ms, 1500² = 225만 칸 → 회당 2.0 ms — 캐시 한계를 넘으며 면적 대비 비선형으로 약간 더 비싸짐).
2. 안개 · 길찾기 · 지형 · 체크섬 · 보급은 면적에 거의 안 민다 (아래 구간표). 안개 갱신은 0.12~0.42 ms, 길찾기 (경로 · 흐름장 계산) 는 이 장면들에서 사실상 0.
3. **60 Hz (틱당 16.7 ms) 예산 안에서 5단계 전부 1000기 · 3000기 안전.** 최악 평균 5.9 ms (1500² 3000기), p95 ≤ 8.7 ms. 유일한 우려는 가끔 나오는 **스파이크** (1200² · 1500² 흩어진 장면에서 최대 30~70 ms, 아래 4절).
4. 메모리는 문제 없음: 1500² 3000기 작업 집합 약 170 MB (6 GB 한계의 3%).

## 4. 스파이크 (최대값) 관찰

- 800² 이상 흩어진 장면에서 최대 13~70 ms (1200² A 3000 52 ms, 1500² A 1000 62 ms / 3000 70 ms). 평균 · p95 는 정상이므로 드문 한 틱. 가능성: 지도 크기 배열 (LOH) 때문에 생기는 gen2 GC, 또는 안개 시차 갱신이 한 틱에 몰리는 경우. 구간 프로파일은 평균만 내므로 정확한 구간은 못 짚었다 (후속: Prof 에 최대값 슬롯). 교전(C) 장면은 최대 12 ms 이하라 깔끔.
- 60 Hz 에서 70 ms 한 번 = 4틱 늦음 (눈에 띄는 끊김 1회). 빈도는 300틱 중 1~2회 수준.

## 7. 권고 (적용 안 함, 사용자 검토용)

1. **`RebuildHash` 를 면적 비례에서 유닛 비례로** (효과 가장 큼, 1500² 에서 틱 -4 ms 이상):
   - 칸 전체 `Array.Clear` 대신, 지난 틱에 점유했던 칸 (`unitCell[i]`, n 개) 만 되돌려 지우기 → `cellMask` · `coarseMask` · `cellStart` 0 으로.
   - `cellStart` 접두합 + `cellCursor` 복사는 점유 칸을 정렬해 처리하거나, 칸 → 슬롯 대신 정렬된 유닛 번호 배열 (counting sort 를 거친 칸 키 정렬) 로 교체. 결과 순서 (칸 안 내림차순) 를 그대로 유지해야 결정성 · 골든이 안 깨진다 — 순서 보존이 핵심이라 opus 급 작업, `--detcheck` GOLDEN 유지 필수.
   - 대안(더 작은 변경): hash1 은 AI/명령 질의용인데 `hashDirty` 일 때만 필요 — 유닛 이동이 없는 틱 · 질의가 없는 틱에는 건너뛰기 (이미 `hashDirty` 로 일부 처리 중. 틱 경계에서 항상 dirty 라 사실상 매 틱 두 번).
2. 1번을 안 하더라도 **60 Hz 예산은 이미 충분** (최악 5.9 ms / 16.7). 다만 배속 (×4~×8) 이나 느린 PC 에서는 1500² 가 먼저 한계에 닿는다 — 1번의 가치는 거기서 나온다.
3. 스파이크 (4절) 는 Prof 에 구간별 최대값을 추가해 원인 (GC / 안개 몰림) 부터 확인. GC 라면 `GCSettings.LatencyMode` 나 큰 배열 재사용 검토.
4. 자동 지도 크기 규칙 (인원 × 20000 칸) 은 그대로 안전. 대형 · 초대형을 사용자가 고를 때 경고 문구는 불필요 (생성 3 s 이하, 작업 집합 < 200 MB).
5. 후속 시험 제안: AI 켠 16세력 · 먼 거리 경로 (구역 그래프) 를 대형 이상에서 `--stress ai players=4 map=1200` 로, 그리고 렌더 시간은 실제 창으로 수동 측정.

재현: `dotnet build -c Release -p:OutputType=Exe -p:IntermediateOutputPath=obj/n13/ -p:OutputPath=bin/n13/` 후 `bin/n13/KoreanDivision.exe --mapload size=1200 k=3000 scene=A`.

## 8. N16 결과 (2026-10-19, 브랜치 `n16`)

시뮬 의미 · 저장 형식 · 체크섬은 그대로 (`--detcheck` GOLDEN, `--update` 없이). 두 가지를 고쳤다.

### 8-1. 공간 해시: 면적 비례 → 유닛 비례 (`World.RebuildHash`)

- 예전: 틱마다 2회 `Array.Clear(cellStart / cellMask / coarseMask)` + 지도 전체 접두합 + `Array.Copy` = O(칸 수).
- 지금: `cellStart[c]` (시작) + `cellCount[c]` (개수) 두 배열. 지난 재구성에서 점유한 칸 목록 `occCells` 만 되돌려 지우고 (count · 세력 비트 · 8×8 묶음 비트),
  이번 점유 칸만 기수 정렬 (11비트 LSD, 칸 번호는 유일하므로 결과 유일) 해서 시작 위치를 매긴다. 빈 칸의 `cellStart` 는 낡은 값일 수 있으나 count 0 이라 구간은 항상 빈다.
- 순서 보존: `sortedIdx` = 칸 오름차순 · 칸 안 유닛 번호 내림차순 — 예전과 비트 단위로 같다. `Separate` 의 "행의 연속 칸 = 정렬 배열의 연속 구간" 순회는 칸별 순회로 바꿨고 순서는 같다.
- 검증: 새 자체 시험 `KD_SELFTEST_ONLY=hash` (`Tests/SpatialHashSelfTest.cs`) — 무작위 배치 · 같은 칸 몰림 · 지도 밖 좌표 · 칸 사이 이동 · 유닛 증감 · 빈 월드 · 8 의 배수가 아닌 지도에서 칸별 목록 · 전체 순서 · 반경 질의 · 세력 비트를 무차별 기준과 비교 (이 시험이 점유 목록 배열을 키울 때 옛 목록을 잃는 버그를 바로 잡아냈다).

### 8-2. 스파이크 원인 = 포탄 구덩이 하나가 지도 전체 재계산을 부름

- 구간별 최대 · p99 와 최악 5틱 분해 (GC 세대별 횟수 · 지형 편집 수 포함) 를 `--mapload` 에 추가했다 (`SECMAX` · `WORST` · `TERRAIN` · `GC` 줄).
- 30~70 ms 틱은 전부 `점령·보급` 구간 (UpdateShells → Explode → `TryCrater`) 에서, **포탄 구덩이가 생긴 바로 그 틱**에만 나왔다. GC 는 측정 구간 내내 0회, 안개 · 길찾기는 무관.
- 경로: `GameMap.Set` 이 `terrainDirty` 를 올림 → 다음 지형 질의에서 `BuildTerrain` 이 지도 전체의 숲 깊이 · 칸 표시 · 지형 해시를 새 배열 2개로 다시 만듦 (1500² = 225만 칸 × 8이웃) + 참호 묶음 `TrenchComps` 가 지형 해시가 바뀌었다고 지도 전체 BFS + `int[칸 수]` (9 MB) 재할당 + 전술 AI `TacMap` 도 지형 해시를 열쇠로 써서 전체 해시 재계산.
- 수정 (결정성 중립 — 파생 캐시의 무효화 열쇠만 바꿈):
  - 숲 깊이 · 가옥 옆은 숲 · 가옥 칸에만 의존하므로, 옛 · 새 지형이 둘 다 숲 · 가옥이 아니면 (풀/흙/모래 → 구덩이 등) 구조 재계산을 하지 않는다. 지형 해시는 따로 `terrainHashDirty` 로 물을 때만 (체크섬) 같은 공식으로 다시 계산 → 체크섬 값 동일.
  - `GameMap.TerrainVersion` (지형 · 고지 변경마다 +1) · `TrenchVersion` (참호 칸이 생기거나 없어질 때만 +1) 추가. 참호 묶음은 `TrenchVersion`, `TacMap` 은 `TerrainVersion` 을 열쇠로 쓴다 (값은 지형의 순수 함수라 다시 계산하는 시점만 달라짐).
