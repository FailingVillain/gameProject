# 미션/지도 편집기 설계서 (Korean Division Mission Editor)

작성: 2026-10-19 · 상태: 설계안 (구현 전) · 위치: `game-tools/mission-editor/`
결정 (사용자 2026-10-19): 게임 안 기능이 아니라 **별도 도구**로 만든다.

## 0. 조사 요약 (현 게임 형식)

- 미션 = `assets/missions/<id>.json` 한 파일. 로더 `MissionDef.Load/Parse` 가 `Validate(Defs)` 를 부르고, `Require` 가 `InvalidDataException` 을 던진다 (첫 오류에서 중단).
- 주요 필드: `id title date location briefing seed weather time player spectate`, `factions[]` (`name en lang color team posture area aiProfile aiWithdrawAt aiCommitment`), `map` (이름 참조) 또는 `mapData` (지형 내장), `areas{}` (이름 붙은 rect/circle), `deployZones[]` (faction + rect/circle), `forces[]`, `reinforcements[]`, `objectives[]` (capture/eliminate/defend/escort), `failures[]` (losses/keyUnit/timeLimit), `events[]` (when: time/area/objective/killed, do: spawn/message/weather/time/reveal).
- 병력 `MissionForce`: `id faction name at|area facing formation battalionForm battalion companies[] units{} rank squadLeaderRank officerRanks officerXp tag company deployable time posture aiArea`. 중대 = `units{유닛id:수}` + 계급 필드, 대대 = `companies[]`.
- 지도 `MapFile`: `width height base`, `paint[]` (`terrain` + `rect`/`circle`/`tiles`), `starts[]`. 지형 enum `TerrainType` = Grass Dirt Sand Water Rock Forest Rubble House Wire Trench Crater. 고지는 별도 bool 층 (`high`), paint 에서 `"terrain":"high"`. 도로 = Dirt, 강 = Water, 마을 = House(+Rubble). **도로 · 하천 · 다리는 별도 타일 종류가 없다** (프리셋으로 표현, 질문 4).
- 세력/유닛 id: `Defs.Units` (balance.json), 한국군 전용 `koreaOnly` (세력 `en != "korean"` 이면 Validate 오류), 계급은 `RankNames.Snap(en, rank)` 로 세력별 사용 계급만 허용 (아니면 경고).
- 기존 도구: `tools/bn_campaign/gen_scen*.py` (시나리오 JSON 생성), `tools/import_kd1920.py` (원본 에셋 import). 모두 JSON 을 직접 쓰는 일회성 스크립트로 검증 수단이 없다.
- 동기 버그: `docs/BUNCHING_DIAG_2026-10-19.md` — `ai_kr_vs_ft_1000` 에서 배치 대형이 지도 밖/장애물에 걸려 시작 5초 안에 가장자리 중대가 한 덩어리가 됨 (nn 0.38~0.5, 겹침 0.9 이상). 편집기는 **중대 풋프린트가 겹치거나 지도 밖/통행 불가 타일에 걸리면 막아야** 한다.
- 첫 사용처 (HANDOFF): N26 마적떼 세력, N27 챕터 0 튜토리얼 (마적 습격 -> 압록강 도하 -> 마적 연합 토벌), N28 챕터 1 (에피소드 8 x 미션 3~4). 미션이 수십 개가 되므로 손으로 JSON 을 쓰는 것은 비현실적이다.

## 1. 목표 / 비목표

**목표**
1. 게임이 이미 읽는 `assets/missions/*.json` 을 **그대로 열고 저장** (새 런타임 형식 없음). 저장물은 게임이 수정 없이 로드해야 한다.
2. 게임과 **동일한 검증** (`MissionDef.Validate`) 을 편집 중 보여주고, 게임이 못 잡는 문제 (배치 겹침, 지도 밖, 통행 불가) 는 편집기 린트로 잡는다.
3. 지형 칠하기, 병력 배치 (분대/중대/대대 + 방향), 배치 구역, 목표/패배 조건, 날씨/시간을 시각적으로 편집.
4. "테스트 플레이" 한 번으로 `--mission <id>` 실행.
5. 기존 6개 미션이 열기 -> 저장 시 **의미 변화 없이 왕복** (round-trip) 되어야 한다.

**비목표**
- 게임 내 편집 모드 (결정됨).
- 유닛/밸런스 편집 (`balance.json` 은 읽기 전용 참조).
- 전투 시뮬레이션 자체 구현 (테스트 플레이는 게임 exe 에 위임).
- 스프라이트/아트 제작, 새 지형 종류 추가 (게임 쪽 일).
- 협업/버전 관리 UI (git 사용).

## 2. 기술 선택

| 게임 타일로 지형 미리보기 | `Terrains`/`MapFile`/`GameMapTerrain` 과 같은 색, 같은 고지/경사 판정 | 색표 복제 | 색표 복제 |
| 통행 가능/대형 겹침 린트 | `GameMap`/Nav/대형 로직 재사용 | 재구현 | 재구현 |

| 사용자 기존 도구와 스택 | 게임과 같은 스택 | ptViewer, lotto 등에서 이미 사용 | 새 스택 |
| 유지보수 | 게임 형식과 같은 버전에 묶임 (장점이자 결합) | 형식 바뀔 때마다 이중 수정 | 이중 수정 + 파일 접근 제약 |
| 배포 | exe 하나 | Python 환경 | 로컬 서버/파일 API |

**권장: (a) C# + Raylib, 게임 `src/Core` 를 참조.**
이 도구 가치의 대부분이 "게임이 읽는 그대로 검증/렌더" 이고, (b)(c)는 검증 규칙과 타일 규칙을 복제해 형식이 바뀔 때마다 조용히 어긋난다 (`koreaOnly`, `aiWithdrawAt`, 계급 Snap 처럼 규칙이 계속 늘고 있다). UI 위젯 부족은 화면이 목록 + 속성 폼 + 캔버스 위주라 감수할 만하다.

**구조 (결합 최소화)**
- 게임 `src/Core/**` 중 UI/렌더 비의존 부분을 편집기가 참조. 현재 `KoreanDivision.csproj` 는 단일 exe 이므로 (1) Core 를 별도 클래스 라이브러리로 분리하거나 (2) 편집기 csproj 가 `Compile Include` 로 소스를 링크하는 두 방법이 있다. 소스 링크로 시작하고 부담이 크면 분리 (질문 6).
- 편집기는 자체 Raylib 창/입력/UI 를 가진다. 게임과의 코드 공유는 Core 뿐.
- 보조: 게임 exe 의 `--mission-validate <file>` (§5) 로 최종 판정.

## 3. 기능 (단계별)

### MVP
1. **열기/저장**: 미션 목록 + 파일 대화, 저장, 다른 이름으로 저장, 새 미션 (템플릿: 2세력, 144x144 풀밭, 주 목표 1개). 저장은 게임 형식과 동일 JSON (키 순서 고정, 한국어 그대로). 기존 파일의 `//` 주석은 보존이 어려울 수 있음 (질문 2).
2. **지형 칠하기**: 브러시 (점/사각/원/선/채우기), 지형 10종 + 고지 층, `base` 타일, 지도 크기 변경, 줌/이동, 격자. 프리셋: 도로 (Dirt 선), 강 (Water 띠), 마을 (House 군집 + Rubble), 참호선 (Trench), 철조망 (Wire), 구덩이 (Crater). `paint[]` 로 저장 (사각/원은 도형 그대로, 자유 칠하기는 `tiles`). `map` (이름 참조) 미션은 지형 읽기 전용으로 열고, "내장으로 복사" 로 `mapData` 변환.
3. **병력 배치**: 세력 선택 -> 팔레트 (유닛 id 는 `Defs` 에서 로드) 에서 분대/중대/대대 구성. 중대 편성 `units{}`, `formation`, `rank`/`squadLeaderRank`/`officerRanks`, 대대는 `companies[]` + `battalionForm`. 지도에서 끌어 놓기 + 방향 핸들 (`facing`), `tag`, `deployable`, `posture`, `aiArea`. 증원 (`reinforcements`) 은 같은 편집기의 별도 탭.
4. **배치 구역**: `deployZones` 를 세력 색으로 사각/원 그리기. `areas{}` 이름 구역 (목표/AI/사건이 참조) 도 그리며, 이름 변경 시 참조 자동 갱신.
5. **목표/승패**: 목표 4종과 패배 3종을 폼으로 편집. 구역/태그 참조는 존재하는 것만 드롭다운.
6. **환경/세력**: 날씨, 시간, 시드, 플레이어 세력, 세력 목록 (`en` 은 목록 선택), `posture`, `aiProfile`.
7. **검증 패널** (실시간, 항목 클릭 시 해당 객체로 이동):
   - 게임 규칙: `MissionDef.Parse` 결과 (오류/경고). 첫 오류에서 멈추므로 `ValidateAll` 추가 권장 (§5).
   - 편집기 린트: (i) **배치 겹침** — 같은 세력 모든 중대/대대의 풋프린트 (대형 폭 x 깊이, `facing` 반영) 가 서로 겹치거나 지도 밖/통행 불가 타일 (Water, Rock, Wire, House 등) 에 걸리면 오류. 풋프린트 계산은 게임의 대형 슬롯 함수 (`OrgFormation`/`Formation`) 호출로, 복제 금지. `ai_kr_vs_ft_1000` 가 회귀 케이스. (ii) `deployable` 병력이 배치 구역 밖이면 경고, 상대 세력 구역끼리 겹치면 경고. (iii) **세력 제한**: `koreaOnly` 유닛은 `en != "korean"` 세력에서 팔레트 회색 + 오류. (iv) 계급 Snap 경고 표시. (v) 끊어진 참조 (구역/태그/증원/목표 id), 주 목표 없음, 도달 불가 목표 (지도 연결성) 경고.
8. **테스트 플레이**: 저장 (또는 임시 사본) 후 게임 exe 를 `--mission <id>` 로 실행. 임시 사본이 `assets/missions/` 를 오염하지 않도록 `--mission-file <path>` 추가 제안 (질문 3). 옵션: `--mission-start` (배치 건너뛰기), 시드, 관전. 게임 로드 오류는 편집기 하단 로그 탭에 표시.

### Phase 2
- **사건/트리거**: `events[]` 를 "언제 (시간/구역 진입/목표 상태/태그 전멸) -> 무엇을 (증원 투입/메시지/날씨/시간/목표 공개)" 카드 UI 로. 증원은 목록에서 선택하고 지도에 진입 위치 표시, 구역 조건은 지도 위 하이라이트.
- **브리핑**: `title date location briefing` 과 목표 텍스트를 한 화면에서 편집, 줄바꿈 미리보기. 새 글자가 폰트 글리프 수집 (`AllText()`) 에 필요한지 점검.
- **세력별 AI 파라미터**: `aiProfile`, `aiWithdrawAt` (0 이상 1 미만), `aiCommitment` (0~1) 슬라이더 + 범위 검증, 기본값 대비 표시. 병력별 `posture`/`aiArea`.
- 스탬프/템플릿 (마을, 참호선, 중대 진형) — `gen_scen*.py` 가 하던 반복 생성을 대체. 다중 선택, 복사/붙여넣기, 대칭 편집, 되돌리기 심화.

### Phase 3
- **캠페인 챕터 연결**: 챕터 -> 에피소드 -> 미션 그래프 (분기/결말) 노드 편집. 게임에 캠페인 데이터 형식이 아직 없으므로 (N28 은 로드맵 단계) **게임 쪽 형식이 먼저 확정**되어야 한다. 편집기는 그 형식의 읽기/쓰기 화면만 추가.
- 챕터 단위 일괄 검증, 미션 요약표 (병력/예상 시간 메모).
- 선택: `--mission-run <id> --verify` 연동으로 "AI 대 AI 완주 가능" 점검을 편집기에서 실행.

## 5. 데이터 흐름과 형식 동기화

```
 assets/missions/*.json --(MissionDef.Parse)--> 문서 모델 (게임 DTO 그대로)
        ^                                              |  편집 / 린트
        |                                              v
        +----------- 저장 (게임 DTO 직렬화) <---- 편집 결과
                                                       |
                                  테스트 플레이: 게임 exe --mission[-file]
```

1. 문서 모델은 게임의 `MissionDef`/`MissionForce` 등 **같은 클래스** (Core 참조). 필드가 추가되면 컴파일/역직렬화로 즉시 반영되고, 편집기 UI 가 모르는 필드는 그대로 보존 (알 수 없는 속성 보관, 게임 DTO 에 확장 데이터 도입 여부는 질문 2).
2. **검증은 게임 코드 호출** (`MissionDef.Parse`). 규칙이 바뀌면 편집기를 다시 빌드하면 끝. `Validate` 는 첫 오류에서 던지므로 편집기용 **`ValidateAll()` (오류 + 경고 목록)** 을 게임에 추가하고 `Parse` 가 이를 감싸게 하는 것이 최선 (게임 동작 불변, 질문 5).
3. **안전망**: 게임 exe 에 `--mission-validate <file>` (오류 목록 출력 후 종료) 추가. CI/스크립트와 편집기 "게임으로 검증" 이 같은 경로를 쓰며, Core 링크가 낡아도 최종 판정은 exe.
4. **골든 테스트**: `assets/missions/*.json` 전부를 편집기 모델로 열고 저장해 정규화 비교로 의미 동일을 확인. 형식 변경 시 즉시 깨져 드러난다.
5. 별도 JSON Schema 는 만들지 않는다 (이중 관리).
6. 지형/대형 의존 린트 (풋프린트, 통행 가능) 는 반드시 Core 함수 호출. 게임 대형 로직이 바뀌면 자동 반영.
7. 읽기 전용 입력: `balance.json` (유닛 id, koreaOnly), `ranks.json`. 게임 폴더 경로는 설정 파일 하나 (`editor.settings.json`) 에 저장.

## 7. 위험

1. **Raylib UI 부담**: 텍스트 입력, 드롭다운, 스크롤 목록을 직접 만들어야 해 예상보다 오래 걸릴 수 있음. 완화: raygui 류 도입 또는 소수 컴포넌트 (버튼/입력/드롭다운/목록) 로 한정해 먼저 만들고 재사용.
2. **Core 분리 비용/병합 충돌**: Core 가 UI/Raylib 타입을 참조하면 분리가 어렵고, 게임이 계속 바뀌어 충돌 가능. 완화: 소스 링크로 시작.
3. **결정론 오염**: 편집기는 Core 를 호출만 하고, 게임 코드 수정은 `ValidateAll`/CLI 옵션처럼 sim 비영향 범위로 제한 (checksum/FormatVersion 불변).
4. **왕복 손실**: 주석, 키 순서, 모르는 필드가 사라짐 -> 골든 테스트와 확장 데이터 보존으로 완화.
5. **풋프린트 린트 오탐/미탐**: 실제 행군 중 종대 전환 (`CheckNarrow`) 은 동적이라 정적 린트로는 일부만 예측. 배치 시점의 겹침/지도 밖/통행 불가만 확정 오류, 나머지는 경고.
6. **형식 확장 속도**: 게임이 새 필드 (N26 마적떼, 튜토리얼 트리거) 를 계속 추가 -> 편집기 UI 가 뒤처짐. 완화: 모르는 필드를 고치는 "원본 JSON" 텍스트 탭 제공.
7. **Phase 3 불확실성**: 캠페인 형식 미정. 앞서 만들면 폐기될 수 있음 -> 형식 확정 후 착수.
8. **경로/OneDrive**: 한글 경로 (`바탕 화면`) 와 OneDrive 동기화 중 파일 잠김. 저장은 임시 파일 작성 후 교체.
